## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
decision-53 section 7 (wave 3) moves content/_data/site.json onto the registry as the `site` namespace: the 48 rows of site/setting-rows.ts become setting declarations with fileKey where the file spelling differs (url, postsPerPage and so on), so the file does not change. SiteSettings becomes the namespace's values type. This task is the read side: readSiteSettings and its 43 callers move to `settings.values(SITE)` or `settings.get`, and the sync-only chains named in the record are redesigned rather than awaited in place: the sync Renderer takes a site snapshot its handler awaited, settleConfig moves into serve(), host.siteInfo() returns a Promise (a plugin API break, released as a major together with wave 4), relays.sync() and the reply-notice listener become fire-and-forget async, and IndieAuth and Micropub read the settled config.baseUrl. The write side (pages saving through `set`) is the next task; readSiteSettings and readSiteJson are deleted here, updateSiteSettings is deleted there.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Registry: fileKey on SettingDeclaration (a string, or several file keys for one composite value such as license), used by read, set and checks; tests first.
2. settings/site.ts: SITE namespace over content/_data/site.json, one declaration per SiteSettings key with the row's read behaviour as the type's fromJson and its write behaviour as toJson (undefined removes the key), fileKey where the file spelling differs, site.base_url override from config.baseUrlSource. license becomes one composite setting over license and licenseName. Round-trip test over apps/demo site.json and the existing row read tests.
3. SiteSettings becomes ValuesOf<typeof SITE> (snake_case keys): rename every property use with a TypeScript language-service codemod, then fix the rest by typecheck. settingsFromSiteJson/siteJsonFor (kept for updateSiteSettings until TASK-389) parse and write through the SITE declarations, so the rows lose their read and write halves now and there is one parser.
4. Benchmark values(SITE) through the lock against today's readSiteSettings (median of interleaved runs); decide per-request snapshot vs per-call reads.
5. Move readers group by group, running the affected tests after each: request handlers and admin (await values/get or read the request snapshot); renderer and page-sources take the site snapshot as a request input (drawnWith), never the registry; MailService.from/theme chosen/provider choice; relays.sync and reply-notices listener fire-and-forget async; IndieAuth/Micropub read config.baseUrl; host.siteInfo() returns a Promise and both plugins that call it are updated.
6. Boot: settle the base URL without readSiteSettings; createCms stays sync.
7. Delete readSiteSettings and readSiteJson (and their export from the package API). Test that undeclared keys survive a set.
8. Docs (plugins.md siteInfo, public-api.md), full verification (build, test, typecheck, lint, format:check) and a curl session on a scratch site.

## Implementation Notes

Step 1-3 done: registry fileKey (one key, or several for one value); SITE declared in site/namespace.ts (site/ layer, since its parsing needs site/ and content/ rules; injected into the registry through a new core option by createSettings); SiteSettings = ValuesOf<typeof SITE> with snake_case keys, renamed across the package by a TypeScript language-service codemod (510 references) plus the settings templates; settingsFromSiteJson/siteJsonFor now parse and write through the SITE declarations, so setting-rows lost its read and write halves. Golden (settings-golden.json) regenerated and compared frame by frame against the old one after mapping keys: every settings, form and problems frame identical; the only byte difference in rewritten files is that licenseName keeps its place instead of moving after license. Full cms suite 5841/5841 with temporary readSiteSettings shims still in place.

Step 4, benchmark (scratch script, demo content copied, interleaved, 9 runs per side of 2000 calls each, plus 150 home page requests per run through cms.app.request, Node 24 on this Mac): readSiteSettings median 16.4 µs (16.0-17.3); settings.values(SITE) through the per-file lock median 37.6 µs (36.5-40.5); GET / median 740 µs (707-823). Both readers returned the same title and posts_per_page and every home page was a 200 with the title. The 21 µs gap is about one third process.env lookups (48 settings each ask for GEEKITY_SITE__<KEY>; with a plain-object env values() is 30.4 µs) and the rest the lock's promise hop and building the resolved values. Decision: read values(SITE) once per request in the app middleware (c.var.site, and RequestInputs.site for the renderer), so a request pays one read, about 5% of a home page, instead of one read per helper. Handlers read c.var.site; background work (mail, IndexNow, notify, retention, relays, reply notices, backfill) reads the registry once per unit of work.
Before step 4: boot and the CLI built the registry with createSettingsRegistry, which has no site namespace, so every request threw 'There is no settings namespace site' once the middleware read values(SITE) (1032 failures). Boot, the CLI and the test registry helper now use createSettings. The conversation reader takes a ConversationSite per call; reply contexts take the site for held replies (read(target, site), stored(target) for the file alone); reply notices are fire-and-forget on their own queue with settled() in the lifecycle; relays.sync() is async on a read queue that settled() waits for; federation contexts are built per use with a cited reader over the site read then. Suite back to 5841/5841.
