## Context

doc-1 put a plugin system out of scope and left two hooks, `onDocumentChange` and `onPublish`. Site code can reach further only from a `server.ts` that calls `createCms`: `cms.app` for routes registered after core's, `cms.events` to observe document changes, `cms.renderer.environment` for public filters. The Docker image runs the generic `geekity serve` with `content/`, `data/` and an optional read-only `themes/` mounted, so a site deployed that way runs no code of its own.

On 2026-10-06 the owner asked for plugins, because some logic is useful to some sites and should not be in core. They named the first users:

- **WordPress compatibility.** decision-14's switch, `wordpressActivityPub` in `site.json`, mounts a second Fedify federation at `/wp-json/activitypub/1.0/` for a site moving from the WordPress ActivityPub plugin. It records each request in `data/wordpress-activitypub.json` and shows the record on Federation > Settings. Beside it sit the `geekity import wordpress-actor` command and the `wordpressActorId` field on every user record. A site born on the CMS never needs any of it.
- **An LLM service.** One consistent API that other plugins use to call a language model, so that no plugin rolls its own client. OpenRouter is the likely first provider.
- **Two consumers of it.** One suggests a post's title and description. The other suggests tags for a post, ranked by how many people follow each tag on tags.pub.

The owner asked for the infrastructure and the use cases to be built hand in hand, so that each piece of core exists because a plugin needs it. They also asked that plugins may depend on each other, and that the design keep the Docker deploy in mind.

The inventory of the WordPress code (2026-10-06) found exactly one switch, read once per request in `wordPressGate` (`src/federation/mount.ts`). The rest of what looks WordPress-shaped is core by decision:

- Stored actor and object ids, served at their URLs and listed as WebFinger aliases, are identity (decision-14: "nothing about this is WordPress-specific").
- The `/feed/`, `/author/`, `/tag/` and `/category/` layout is the site's URL design.
- oEmbed and the embed frame serve any consumer.

tags.pub (Social Web Foundation) runs one ActivityPub `Service` actor per hashtag at `https://tags.pub/user/<tag>`. Its public `followers` collection carries `totalItems`. Any string returns an actor, so a count of zero means nobody follows the tag. tags.pub has no search and no popular-tags endpoint.

OpenRouter speaks the OpenAI chat-completions shape at `https://openrouter.ai/api/v1/chat/completions` behind a bearer key. It takes `response_format: {type: "json_schema", ...}` on models whose `supported_parameters` list it. It reports usage on each response and returns typed errors: 401, 402 for no credits, 429 and 503 with `Retry-After`. OpenAI and Ollama accept the same shape at their own base URLs.

## Decision

- **A plugin is a named module.** It declares `name`, `label`, `description`, `requires` (the names of the plugins it depends on), optional `settings`, and a `register(host)` function. Its name is its npm package name, such as `@geekity/plugin-llm`, which npm already keeps unique; a plugin installed by hand declares a package-style name in its manifest, and two plugins with one name refuse to load. The host passed to `register` is the plugin's only door into the CMS. A plugin imports nothing from core but types.
- **Every installed plugin registers at boot, and the site enables the ones it uses.** Enabling and disabling take effect on the next request, without a restart, because an operator on Docker cannot restart the container from the admin. Core routes each request to a plugin's contributions, such as routes, middleware, admin screens and editor actions, only while that plugin is enabled. A disabled plugin's routes fall through as if absent. A plugin may have `start` and `stop` hooks for timers and caches. Core calls them on enable, on disable, at boot for enabled plugins and in `close()`.
- **The enabled set is a site setting.** It is the `plugins` key in `content/_data/site.json`, an object keyed by package name, alongside the other settings and written the same way. A plugin's public settings live under its key there. Each plugin has a private folder, `data/plugins/<package name>/` (for example `data/plugins/@geekity/plugin-llm/`), and its secret settings live in `secrets.json` there, mode 0600. An environment variable overrides a secret, named `GEEKITY_PLUGIN_` plus the package name and the setting in upper case with every other run of characters as `_`, such as `GEEKITY_PLUGIN_GEEKITY_PLUGIN_LLM_API_KEY`. The plugin's screen prints each variable's exact name. Two installed packages whose names map to one prefix refuse to load, so a Docker operator can keep a key in `.env`. The admin then shows that setting as set by the environment and does not edit it.
- **Dependencies are names, resolved at boot and checked on every change.** Every installed plugin registers at boot, in any order, because no plugin can reach another during `register`. The dependency graph decides which plugins are available and which can be enabled. It also orders `start`, dependencies first, and `stop`, dependents first. An installed plugin whose dependency is missing, or that sits in a cycle, is unavailable. The Plugins screen names the reason. The site still boots, so a broken plugin never takes the site down. A plugin cannot be enabled until every plugin it requires is installed and enabled, as WordPress handles `Requires Plugins`. Its row names what is missing, and nothing is installed or enabled on the operator's behalf. Keeping that step manual also discourages tiny utility plugins that many others pull in. Disabling a plugin that enabled plugins require is refused, and the refusal names them. Versions follow the packages: a plugin package peer-depends on `@geekity/cms` and on each plugin package it requires, with a semver range. npm checks those ranges for a site that installs with npm. For a folder install, the manifest beside the bundle carries the same ranges and the registry checks them, so a plugin whose dependency is out of range is unavailable, with the reason.
- **Plugins share services by name.** A plugin provides at most one service, named by the plugin's package name: `@geekity/plugin-llm` calls `host.provide(service)` in its `register`, and a plugin with several things to offer puts them on that one object (`host.use('@geekity/plugin-llm').querier`), so a service name can never collide and `use` always names a plugin in `requires`. A dependent calls `host.use('@geekity/plugin-llm')` when it handles a request or a job. Every consumer gets the same instance. `use` throws during `register`, so by the time any plugin can call it, every plugin has registered and every service exists. The types come from a declaration map that the providing plugin augments, so `use('@geekity/plugin-llm')` is typed without a cast. `use` on a name that is not in `requires` is a type error and a boot error. Because each bundle inlines its own copy of its npm dependencies, two plugins never share a library instance. A service therefore passes plain data and the host's own types across the boundary, never an object built by a library. Plugin B's copy of a library would fail an `instanceof` check against plugin A's.
- **Core grows an extension point only with its first consumer.** The milestone builds each point in the same task as the plugin that needs it:

  | Extension point | First consumer |
  | --- | --- |
  | Registry, dependencies, enable/disable, the Plugins screen, the `@geekity/cms/plugin` export, `plugins` in the config | An example plugin in `apps/demo` |
  | A middleware phase in the federation mount, access to the site federation's KV and handlers, plugin data files, CLI commands | WordPress (the second federation, its request record, `import wordpress-actor`) |
  | Settings and secrets, drawn as a form from the plugin's declared fields | LLM |
  | Services between plugins | LLM, used by post summaries |
  | Editor actions, plugin admin JSON endpoints and plugin static scripts | Post summaries |
  | An outbound fetch that refuses private addresses unless the site allows them, with a cache in `data/` | Tag suggestions (tags.pub) |
  | A folder of plugins installed by `geekity plugin add`, loaded by a supervised reload | WordPress on Docker |

  A host API with no consumer is not added. MCP tools from plugins wait for M27.
- **The WordPress plugin takes the switch and everything behind it.** That is the second federation and its gate, the request record, the import command, the user's WordPress actor id and the Federation > Settings section, which moves to the plugin's own screen. Stored ids, WebFinger aliases, the feed and archive layout, and oEmbed stay in core. The canonical inbox keeps `withIdempotency('per-origin')`, because two federations sharing one KV dedupe on it. That is a core invariant, held by a core test. No deployed site uses the switch: on 2026-10-06 shll.me is the only site on the CMS and does not use it, and andrewshell.org is still on WordPress. So nothing migrates. The setting, the user field and the code leave core outright, and the plugin keeps its own map from user to WordPress actor id. The removal still carries a BREAKING CHANGE footer for semver.
- **The LLM plugin is one provider shape, the OpenAI chat-completions API.** Its settings are a base URL (OpenRouter by default), an API key (secret), and a default model. The service it provides is:

  ```ts
  complete(request: {
    messages: Message[];
    schema?: JsonSchema;
    model?: string;
    maxTokens?: number;
    signal?: AbortSignal;
  }): Promise<Completion>;
  ```

  A `Completion` is either `{ ok: true, text | value, usage, model }` or `{ ok: false, error }`. The error is one of `unconfigured`, `unauthorized`, `no-credit`, `rate-limited` (with `retryAfter`), `unavailable`, `invalid-output` or `network`. With a schema, the plugin asks for `json_schema` output and sends `provider.require_parameters` to OpenRouter. It validates the reply against the schema whatever the provider claims. A consumer never parses a model's output itself. OpenAI and Ollama work by changing the base URL. Another provider shape, such as Anthropic's Messages API, would be a second implementation of the same service, added when someone needs it.
- **Draft text leaves the server only when a person asks.** An editor action runs on a click and never on save or publish. Every call goes from the server, because the admin CSP's `connect-src 'self'` would refuse a browser call to a third party. That also keeps the key off the page.
- **Plugins are npm packages of their own, versioned independently, kept in this monorepo.** Each lives in `packages/plugin-<name>/` and is published as `@geekity/plugin-<name>`: `plugin-wordpress`, `plugin-llm`, `plugin-post-summary` and `plugin-tag-suggest`. A package names the `@geekity/cms` host API it targets as a peer dependency range. It imports only `@geekity/cms/plugin`, whose `exports` entry is the boundary. A package that consumes another's service, such as `plugin-post-summary` using `@geekity/plugin-llm`, lists that package in `requires` and peer-depends on it with a range, so the name in `requires`, the peer dependency and the argument to `use` are one string. Core ships no plugins and no plugin's dependencies, and the Docker image contains core alone.
- **A plugin's npm dependencies are its own.** They are in the plugin package's `package.json`, never in core's. A site with its own `server.ts` installs a plugin with npm and gets its dependencies the usual way. For Docker, each plugin package's build also emits one self-contained bundle with its dependencies inlined, shipped in the package's `files`. A plugin that needs a native module cannot be bundled and is supported only through npm. The LLM plugin uses no SDK. It calls the HTTP API with Node's built-in `fetch`, so no OpenRouter or OpenAI library is ever installed.
- **On Docker, `geekity plugin add` installs a plugin into a mounted folder.** `GEEKITY_PLUGINS_DIR`, `/site/plugins` in the image, holds one folder per plugin. `docker compose exec cms geekity plugin add @geekity/plugin-llm` fetches the package tarball from the npm registry, checks its integrity hash, and unpacks the bundle and its manifest into `plugins/@geekity/plugin-llm/`. It needs no `npm` and no `package.json` in the container. It installs only the package it is given. When that plugin requires plugins that are missing, the command and the Plugins screen name them, and the operator adds each one. A plugin package marks itself a plugin, and declares its host API range and the plugin packages it requires, in a `geekity` field of its `package.json`; each required package is also a peer dependency with its range. The bundle build writes `plugin.json` from that field. `geekity plugin remove` deletes the folder. A hand-copied folder with a bundled `index.js` works the same way, which is how a plugin not on npm is installed. The bundle's default export is the plugin, and because the host is passed in, it needs no runtime import of `@geekity/cms`, which a mounted folder could not resolve. `geekity serve` becomes a supervisor that owns the port and runs the CMS in a worker. Reload on the Plugins screen boots a new worker beside the old one, which stops writing and drains, so a newly installed plugin loads with no container restart and no refused request. A site with its own `server.ts` passes plugin objects in `plugins` on its config instead. A plugin runs as the site process, with the site's access to `data/`, and the Plugins screen shows each plugin's package, version and where it came from.

## Consequences

- doc-1's "Plugin system beyond the two hooks above" leaves the out-of-scope list. doc-1 gains a Plugins section, and the README gains a section for plugin authors.
- decision-14's paragraph "WordPress's paths are a switch" stays true in effect. The switch is now the `wordpress` plugin, and the cutover's "turn the switch on" means "enable the WordPress plugin". The rest of decision-14 is unchanged.
- The host API joins the semver contract under decision-6. Removing or reshaping a host method is a breaking change to `@geekity/cms`. The host API carries a version number. A bundle declares the version it targets, and a plugin that targets a newer version than the core is unavailable, with a reason. An npm-installed plugin declares the same range as its peer dependency.
- Settings now have two homes per plugin: public values in `site.json` and secrets in `data/plugins/<package name>/`. Both are files, which keeps decision-9. No plugin keeps durable state in SQLite.
- Each enabled-check is a read of `site.json`, which settings already cache per request. Disabled plugins cost one lookup per request and nothing else.
- A reload briefly runs two workers. Only the new one writes: the old one answers reads, refuses writes with 503 and Retry-After, and drains its queues. A worker that crashes is respawned by the supervisor instead of taking the container down.
- The Dockerfile gains `/site/plugins` and `GEEKITY_PLUGINS_DIR`, and `deploy/compose.yaml` gains a plugins volume beside `themes/`. It is writable, because `geekity plugin add` writes to it from inside the container.
- release-please gains one entry per plugin package. `@geekity/cms` keeps `include-component-in-tag: false` so its `v0.x.y` tags continue. Each plugin package sets it to true, so its tags read `plugin-llm-v0.1.0`. commitlint gains one scope per plugin package (`plugin-wordpress`, `plugin-llm` and so on), and the CLAUDE.md scope table lists them. Every plugin package is smoke-tested as installed against the packed `@geekity/cms` tarball, as core is (decision-6).
- Calls to a model cost the site owner money. The LLM plugin shows the usage of its last call on its screen, and no plugin calls the model without a person asking.
- tags.pub has no published rate limits. Tag lookups send a descriptive User-Agent, run a few at a time, and cache counts for a day.
